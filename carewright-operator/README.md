# carewright-operator

This project lives in the [`carewright-operator/`](../) directory of the CareWright monorepo. The Go module path remains `carewright.io/carewright-operator`; build commands and the Docker build context are relative to this directory.

## Description

The carewright operator manages the CPG Ingester and Care Plan Writer pipelines.
Backend processing components run as policy-controlled OpenShell `SandboxRequest`
resources. Each pipeline's BFF and browser UI run as ordinary Kubernetes
Deployments and Services; the UI also has an OpenShift Route. Pipeline
orchestration is a `SonataFlow` resource run by the separately installed
SonataFlow Operator.

## Pipeline configuration

`CPGIngester` and `CarePlanWriter` expose typed configuration for artifact
storage, MLflow tracing, LLM access, external service endpoints, and component
behavior. Each component still owns its image. Sandbox credential fields refer
to named OpenShell providers rather than embedding secret values in environment
variables. Each pipeline controller creates and owns one `SandboxRequest` per
processing component plus BFF and UI Deployments. It removes stale children
and summarizes backend readiness on the parent resource.

`extraEnv` is available on components for non-secret settings that do not yet
have first-class fields. Sandboxed components can also use `extraProviders` and
`policyRef`; these OpenShell-only fields do not apply to UI or BFF Deployments.
All components support `command` and `resources`; the operator supplies the
known image startup command when `command` is omitted. The former component and
workflow `env` arrays are no longer part of the v1alpha1 schema. The samples
under `config/samples` show the complete first-pass fields.

Once OpenShell has generated an HTTP URL for every sandboxed component, each pipeline
controller creates an owned `sonataflow.org/v1alpha08` `SonataFlow` resource
and the matching `<workflow-name>-props` ConfigMap. Component URLs in the
workflow and callback URLs sent to the sandboxes are generated by the operator.
SonataFlow's published address includes the workflow REST path (for example,
`/wcpgingesterworkflow`), while the CloudEvent callback channels are mounted
at the route origin under `/wait-*`. The operator retains the published address
in `status.endpoints.workflow` but strips that path before appending each
callback suffix; BFF `SONATAFLOW_URL` also receives the origin.
The component `SandboxRequest` policies allow egress to the published workflow
host, falling back to the in-cluster Service during bootstrap. The BFF
Deployment receives its generated `SONATAFLOW_URL` and has a stable in-cluster
Service URL. The pipeline reports
Ready only when every sandbox, the BFF Deployment, and SonataFlow are ready.
The separate `Exposed` condition also requires the UI Deployment and Route.

For an external artifact store, configure `artifactStore.credentials` with a
namespace-local Secret containing `ARTIFACT_STORE_ACCESS_KEY` and
`ARTIFACT_STORE_SECRET_KEY`. The BFF Deployment reads those keys through
Kubernetes Secret references; an OpenShell-only `credentialsProvider` cannot
supply credentials to a regular Deployment. For a managed MinIO ObjectStore,
the operator creates a separate credential-only Secret and wires it to the BFF
and sandbox providers. Neither UI nor BFF receives an
OpenShell provider or sandbox policy. On upgrade, the controller removes their
old owned SandboxRequests and the obsolete UI-to-BFF bridge NetworkPolicy.

Install the SonataFlow Operator before enabling the `cpgingester` or
`careplanwriter` controllers. A namespace-wide `SonataFlowPlatform`, when
needed for the chosen profile and supporting services, remains shared
infrastructure and is not owned by an individual pipeline.

## OpenShell sandboxes

A `SandboxRequest` declares an image, command, non-secret environment values,
resource limits, credential providers, HTTP services, and an optional policy
stored in a ConfigMap. The controller uses the official OpenShell Go SDK to
create and observe the sandbox. For every `spec.services` entry, it asks the
gateway to expose the target port and publishes the generated endpoint under
`status.services[].url`. Service-only changes do not replace the sandbox. It
deletes the sandbox when the request is deleted.

`spec.networkAccess` adds typed egress destinations to the effective OpenShell
policy. Pipeline controllers use it to permit calls to their generated
SonataFlow Service without requiring users to edit policy YAML with an
operator-generated hostname.

For local development, make sure the OpenShell gateway is reachable before
running `make run`. Requests should normally set `spec.gateway.endpoint` to a
gateway URL reachable from the manager process. If it is omitted, the controller
uses `OPENSHELL_GATEWAY_ENDPOINT` and `OPENSHELL_GATEWAY_INSECURE`.
`gateway.name` is retained for API compatibility but is not supported by the
SDK-based controller.

For focused local development, run only selected controllers with
`--controllers`. For example, start only the SandboxRequest controller with:

```sh
go run ./cmd/main.go --controllers=sandboxrequest
```

To reconcile only one existing pipeline's SandboxRequests during a local test,
set `SANDBOXREQUEST_OWNER_UID` to that pipeline resource's metadata UID. Requests
owned by other pipelines are ignored; leave it unset for normal operation.

Environment values in `spec.env` are passed on the command line and must not
contain secrets. Attach configured OpenShell credential providers through
`spec.providers` instead. To have the operator register a provider, add a
`credentials` block with an OpenShell profile `type` and a same-namespace
`secretRef.name`. The Secret's data keys must match environment variable
names declared by that OpenShell profile (for example `LLM_API_KEY`), not its
internal credential ID (for example `api_key`). Optional non-secret provider
settings go in `credentials.config`. The pipeline CRs support this under `artifactStore` and
`llm`; CarePlanWriter also supports it under `llmReasoning.embedding` and
`fhirTarget`.

The pipeline controller generates a provider name and passes the Secret
reference to each component's SandboxRequest. The SandboxRequest controller
registers or updates the provider before sandbox creation and watches the
Secret for credential rotation. The existing `credentialsProvider` field
continues to refer to a provider managed outside the operator. Use one form
per integration. Credentials are never stored in the CR or its status. When a request changes
its provider registrations or is deleted, the controller removes an old
provider after no SandboxRequest in that gateway workspace still uses it.
Delete pipeline resources before shutting down the OpenShell gateway so their
finalizers can complete. Referenced Kubernetes Secrets remain user-owned.

See `config/samples/apps_v1alpha1_sandboxrequest.yaml` for a minimal request and
ConfigMap-backed policy.

## Bootstrap prerequisites on OpenShift

Before installing this operator on a fresh OpenShift cluster, run the
[external-prerequisites bootstrap](docs/bootstrap-prerequisites.md). It prepares
MinIO, Agent Sandbox, OpenShell, and SonataFlow, then prints the values needed
for pipeline CRs. It does not create provider instances or install this operator.

## Getting Started

### Prerequisites
- go version v1.25.0+
- docker version 17.03+.
- kubectl version v1.11.3+.
- Access to a Kubernetes v1.11.3+ cluster.

### To Deploy on the cluster
**Build and push your image to CareWright Quay** (run these commands from the `carewright-operator/` directory):

```sh
make docker-buildx IMG=quay.io/carewright/carewright-operator:<tag>
```

The `docker-buildx` target publishes both `linux/amd64` and `linux/arm64`. In the monorepo, `.github/workflows/publish-operator-image.yml` publishes a short-commit-SHA tag to this repository when changes under `carewright-operator/` reach `main`, or when manually dispatched. Ensure the Quay credentials have write access to `carewright/carewright-operator`.

**Install the CRDs into the cluster:**

```sh
make install
```

**Deploy the Manager to the cluster with the image specified by `IMG`:**

```sh
make deploy IMG=quay.io/carewright/carewright-operator:<tag>
```

> **NOTE**: If you encounter RBAC errors, you may need to grant yourself cluster-admin
privileges or be logged in as admin.

**Create instances of your solution**
You can apply the samples (examples) from the config/sample:

```sh
kubectl apply -k config/samples/
```

>**NOTE**: Ensure that the samples has default values to test it out.

### To Uninstall
**Delete the instances (CRs) from the cluster:**

```sh
kubectl delete -k config/samples/
```

**Delete the APIs(CRDs) from the cluster:**

```sh
make uninstall
```

**UnDeploy the controller from the cluster:**

```sh
make undeploy
```

## Project Distribution

Following the options to release and provide this solution to the users.

### By providing a bundle with all YAML files

1. Build the installer for the image built and published in the registry:

```sh
make build-installer IMG=quay.io/carewright/carewright-operator:<tag>
```

**NOTE:** The makefile target mentioned above generates an 'install.yaml'
file in the dist directory. This file contains all the resources built
with Kustomize, which are necessary to install this project without its
dependencies.

2. Using the installer

Users can just run 'kubectl apply -f <URL for YAML BUNDLE>' to install
the project, i.e.:

```sh
kubectl apply -f https://raw.githubusercontent.com/samschifman/carewright/<tag or branch>/carewright-operator/dist/install.yaml
```

### By providing a Helm Chart

1. Build the chart using the optional helm plugin

```sh
operator-sdk edit --plugins=helm/v1-alpha
```

2. See that a chart was generated under 'dist/chart', and users
can obtain this solution from there.

**NOTE:** If you change the project, you need to update the Helm Chart
using the same command above to sync the latest changes. Furthermore,
if you create webhooks, you need to use the above command with
the '--force' flag and manually ensure that any custom configuration
previously added to 'dist/chart/values.yaml' or 'dist/chart/manager/manager.yaml'
is manually re-applied afterwards.
